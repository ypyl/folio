# Plan

One feature at a time, no waterfall. After every step the app builds and runs: we started with the UI shell on mock data, then swapped real implementations in behind the same screens. Numbered entries are the record of shipped work and are never renumbered, so commits and archived changes can point at them. Anything not shipped is below, and becomes a numbered entry only when we commit to building it.

## Decided against

Won't do, with the date and the reason, so the question stays closed.

- **Reference-aware asset deletion** — **won't do** (decided 2026-09-10). Deleting a link stays non-destructive: the asset remains on disk, and the app never scans references to decide whether to delete a file. No reference-aware cleanup and no deletion prompts; the safe default is the decision, not an open question.
- **Page size limits** — **won't do** (decided 2026-09-11). No file-size cap and no degraded mode for large files: they are hypothetical, and any threshold either nags a legitimate file or never fires. A sluggish page is one the user can split in any text editor, which is the point of a folder of plain Markdown. Revisit only on a real stall, and then as crash prevention, not a limit. If it ever happens, the unit is top-level blocks (what the DOM pays for), not bytes.

## Known costs

Measured and left as they are, with the symptom that would reopen them.

- **Long-page typing cost** — **measured, accepted** (decided 2026-09-11). Re-profiled on the production build at 1500 blocks (157 KB): the 53-char burst is 84% native renderer time (1063 ms of 1261 ms sampled), so the per-keystroke term is browser-side and no cheap lever exists (`content-visibility`/`contain` made it worse). The deferred gutter is the one app-side cost the earlier archive under-measured: it runs 3-6 times per burst (the debounced change plus every `ResizeObserver` reflow a layout-changing keystroke triggers), each pass O(blocks) measure plus 1500 span writes, giving a 120-150 ms hitch after typing stops. Left as-is: long pages are hypothetical, and the real fix (per-block widget decorations so the browser positions the numbers, no JS measurement) is a rewrite. Revisit if a real page above ~3000 blocks stalls.
- **Find-in-page over the page listing** — the Pages listing holds only the rows near the viewport, so the browser's own find cannot reach a row scrolled far away (the app's search still covers every note). This is the trade task 23 made; the listing keeps list semantics and a total size so it is not read as short. Revisit if it bites in use.
